#  ErumPay - payment-service

**MSA 기반 QR 간편결제 서비스**  
LG CNS AM Inspire Camp 최종 프로젝트 대상

- **기간:** 2026.04 ~ 2026.06
- **상태:** 종료
- **팀 규모:** 8명
- **담당:** Payment Service의 `core` 도메인
- **저장소:** [ErumPay](https://github.com/ErumPay) · [Payment Service](https://github.com/ErumPay/payment-service)

여러 장의 카드를 가진 사용자가 결제 순간 유리한 카드를 선택할 수 있도록, 결제 데이터를 기반으로 카드 혜택과 실적 조건을 분석해 결제 방식을 추천하는 서비스입니다.

Payment Service의 `core` 도메인을 담당해, 결제 한 건의 생성·승인·취소 흐름과 상태 전이를 구현했습니다. <br>
사용자별 멱등성 처리, 결제 상태 이력 저장, 다중 인스턴스 환경의 이벤트 전달을 다뤘습니다.

### 사용 기술

Spring Data JPA · MySQL · Redis · OpenFeign · Kafka · Docker

### 담당 업무

**결제 한 건의 처리 흐름**을 담당했습니다. 
개별 결제를 처리하고, 결과를 관련 도메인에 전달하도록 구현했습니다.

- 결제 요청 검증과 생성·승인·취소 흐름 구현
- Auth의 PIN 인증, Card의 카드·빌링키 조회, 추천 결과와 PG 요청 연계
- 승인·실패·취소 결과에 따른 결제 상태 갱신과 이력 저장
- 사용자 범위의 멱등성 키를 통한 중복 요청 처리
- 더치페이·원격결제의 개별 결제 수행과 결과 전달
- 다중카드 승인·보상 취소 요청 및 PG 분할결제 API 연계

## 주요 구현과 문제 해결

### 1. 결제 처리 흐름과 상태 이력 저장

결제 요청에서 사용자·금액·카드 구성·처리 가능 상태를 검증하고, PIN 인증과 PG 요청을 연결했습니다. 
승인·실패·취소 결과에 따라 결제 상태를 갱신하고 관련 이력을 저장했습니다.

결제의 현재 상태와 별도로 주요 상태 이벤트를 `payment_events` 테이블에 기록해, 거래 과정을 추적할 수 있는 데이터를 남겼습니다.

| 기록 항목 | 내용 |
| --- | --- |
| 결제 ID | 이벤트와 결제 건 연결 |
| 이벤트 유형 | 생성, 결제 대기, PG 처리 대기, 승인 완료, 실패, 취소 요청·완료 등 |
| 발생 시각·처리 주체 | 이벤트 발생 시점과 사용자·시스템·PG 등의 처리 주체 기록 |
| PG 거래·그룹 ID | PG 응답에서 확보한 식별자 기록 |
| 실패 코드 | 실패 처리 시 확인 가능한 실패 코드 기록 |

더치페이에서는 대표자 가승인과 참여자 결제 등의 목적을 구분하고, 결과를 세션 관리 영역에 전달했습니다. 원격결제 역시 세션의 진행 조건과 실제 결제 수행을 연결했습니다.

### 2. 사용자 간 멱등성 키 충돌로 정상 결제가 차단되는 문제

**문제와 원인**

서로 다른 사용자가 같은 멱등성 키를 사용하면 정상 요청도 중복 결제로 판단되는 문제가 있었습니다. 멱등성 키에 전역 UNIQUE 제약이 적용되어, 중복 판단 범위가 모든 사용자로 설정되어 있었습니다.

**대응**

전역으로 적용되던 멱등성 키의 UNIQUE 제약을 DB에서 `(user_id, idempotency_key)` 조합으로 변경해, 사용자별로 중복을 판단하도록 했습니다. 조회 시에도 사용자 ID와 멱등성 키를 함께 사용했습니다.

결제 준비 단계의 재요청은 종료 여부에 따라 처리했습니다. 종료된 결제는 저장된 정보로 응답하고, 진행 중인 결제는 처리 중 오류를 반환했습니다. 실제 승인 단계에서는 키 일치 여부와 결제 상태를 검사해 이미 처리된 요청을 차단했습니다.

**변경 결과**

동일 사용자의 키 재사용을 제한하면서, 서로 다른 사용자는 같은 키를 사용할 수 있도록 중복 판단 범위를 분리했습니다.

### 3. 다중 인스턴스 환경에 대응한 애플리케이션 이벤트 전달 개선

**문제와 원인**

인프라 담당자로부터 여러 Pod로 운영되는 환경에서 일부 사용자가 카드 추천 결과와 결제 완료 알림을 받지 못한다는 문제를 전달받았습니다. 애플리케이션의 SSE 연결과 추천 데이터가 Pod별 메모리에 있어, 다른 Pod에서 처리된 이벤트를 사용자에게 전달하지 못하는 구조였습니다.

**대응**

Payment Service의 이벤트 전달 로직을 수정해 Redis Pub/Sub으로 인스턴스 간 이벤트를 전파하고, 추천 결과는 TTL을 설정해 Redis에 저장했습니다. 각 인스턴스가 수신한 이벤트를 자신이 보유한 SSE 연결로 전달하도록 애플리케이션 코드를 변경했습니다.

**변경 결과**

이벤트가 발생한 Pod와 SSE 연결을 보유한 Pod가 달라도 전달할 수 있도록 Payment Service의 이벤트 전달 구조를 변경했습니다.


## 배운 점

이번 프로젝트에서 처음으로 백엔드 로직을 구현하며 MVC 구조와 백엔드 애플리케이션의 요청 처리·데이터 저장 흐름을 이해했습니다. Docker·Redis·Kafka 등 다양한 기술을 접하고, 서비스 연계와 결제 상태 저장, 보상 취소 요청을 구현하면서 트랜잭션, MSA, Saga 패턴, 메시지 기반 아키텍처에 대한 지식을 확장했습니다. 특히 결제 생성·승인·취소와 상태 관리를 직접 구현하며 결제 도메인의 기본 흐름을 익혔고, 멱등성 키의 중복 판단 범위를 사용자 단위로 조정하면서 요청의 맥락에 맞게 제약조건을 설계하는 중요성을 배웠습니다.

## 개선 과제

아래는 현재 구현을 바탕으로 정리한 보완 과제이며, 완료한 작업은 아닙니다.

- 동일 사용자·동일 키, 다른 사용자·동일 키, 동시 요청을 구분한 멱등성 검증
- Pod 간 이벤트 전달과 추천 결과 TTL 만료 상황의 재현·기록
- 결제 ID별 상태 이벤트를 조회해 처리 순서를 확인하는 사례 정리
- 보상 취소 결과 검증, 실패 상태 저장과 재시도 방식 검토
- 일부 카드 승인 실패와 보상 취소 실패에 대한 PG 연계 검증
